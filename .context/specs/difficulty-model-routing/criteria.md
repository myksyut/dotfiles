# 判断基準

切替はランタイムが勝手にやらない。**メインエージェントが `set_model` を呼ぶ。**

```
set_model { tier: "easy"|"mid"|"hard", kind?: "design"|"architecture"|"review", reason: "..." }
```

モデル名はエージェントが直接指定しない。tier / kind から `models.json` が決める。

## いつ呼ぶか

1. ユーザーの依頼を読んだ直後、作業に入る前
2. 途中で仕事の性質が変わったとき（調査 → 設計、修正 → レビュー など）
3. すでに同じ tier/kind なら呼ばない

モード切替（`set_mode`）とは独立。PLAN でも easy なら luna、NORMAL でも設計なら fable。

## 判定手順（上から最初に当たったもの）

```
レビュー・品質判定か？
  → kind=review

設計判断・境界・トレードオフが本体か？
  → kind=design または architecture（どちらも fable）

下の easy 条件をすべて満たすか？
  → tier=easy

それ以外
  → tier=mid（省略可。default の grok のまま）
```

迷ったら **mid**。上げるのは「判断が本体」のときだけ。下げられるのは「範囲が明らかに小さい」ときだけ。

---

## review → `gpt-5.6-sol`

仕事の本体が **他人（または直前）の成果物を評価すること**。

やる
- PR / diff / 実装のレビュー
- 「これでいいか」「バグないか」「退行してないか」
- reviewer サブエージェントを出すとき（こちらはロールでも sol）

やらない
- 自分で直しながら見る（それは mid か hard）
- 設計を決める（それは design）

---

## design / architecture → `claude-fable-5`

仕事の本体が **どう作るかの判断**。コード量は関係ない。

やる
- モジュール境界、責務分割、公開 API
- データモデル、スキーマ、永続化の形
- 認証・権限・マルチテナントの方針
- 複数システムをつなぐ、移行計画
- 「A と B どっち？」が残っている状態で方針を決める
- 破壊的変更、互換、ロールアウト
- SPEC / PLAN で方向を固める作業そのもの

やらない
- 決まった設計に沿って実装するだけ（mid）
- 既存パターンのコピー（mid か easy）
- ファイルをたくさん触るだけの機械的リネーム（easy / mid）

`architecture` はシステム全体の骨格。`design` は機能単位の形。どちらも Fable。区別できなければ `design`。

hard も同じモデル。hard は「実装が難しいが設計は決まっている」とき（並行性、セキュリティ修正、微妙な状態機械）。

---

## easy → `gpt-5.6-luna`

次を **すべて** 満たす。

1. 変更範囲が小さい（目安: 1ファイル、または明確な数行）
2. 設計判断がない
3. 失敗しても巻き戻しやすい
4. 正解がほぼ一つ

やる
- 説明、要約、この関数なに？
- typo、lint、format、import 整理
- リネーム、コメント、ログ1行
- 原因が特定済みの小さなバグ
- 「このファイル読んで」だけ

やらない
- 原因不明のバグ（mid）
- テスト設計が要る（mid）
- 「ついでに構造も整えよう」（design / hard）
- 複数パッケージにまたがる（mid 以上）

1つでも外れたら easy ではない。

---

## mid → `grok-4.6`（デフォルト）

既存の形に沿って普通に進める仕事。**迷ったらこれ。呼ばなくていい。**

やる
- 既存パターンに乗った実装
- 数ファイルの bugfix
- テスト追加、リファクタ（境界は変えない）
- 調査のあと、方針が見えている実装

やらない
- 上の easy を全部満たすもの
- 方針がまだない設計

## 例

| 依頼 | 判定 | 理由 |
|------|------|------|
| この関数何してる？ | easy | 読み取りだけ |
| typo 直して | easy | 1箇所、判断なし |
| lint 落ちてるの直して | easy | 範囲が閉じている |
| ログイン失敗する、原因不明 | mid | 調査＋修正、設計は動かさない |
| 既存の repository にメソッド足して | mid | パターン踏襲 |
| 認証をセッションから token に変える方針を決めて | design | 境界とトレードオフ |
| モノリスから worker を分離する | architecture | 骨格 |
| 競合する更新を直す（設計は既存） | hard | 実装が難しい |
| この PR 見て | review | 評価が本体 |
| 仕様書いて | design | 方向を固める |
| 仕様どおりに実装して | mid | 判断は済んでいる |

## やってはいけないこと

- 毎メッセージ `set_model` する
- モデル ID を直指定する（`claude-fable-5` など）
- 「なんか難しそう」だけで hard / design
- PLAN/SPEC に入ったから必ず fable
- 実装しながらレビュー扱いで sol にする
