# ADR フォーマット

ADR は `docs/adr/` に置き、連番で命名する：`0001-slug.md`、`0002-slug.md`、…

`docs/adr/` ディレクトリは**遅延作成**する：最初の ADR が必要になったときに初めて作る。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3文：どういう文脈で、何を決め、なぜそうしたか。}
```

これだけでよい。ADR は1段落で成立する。価値は「決定が**なされたこと**」と「**なぜか**」の記録にあり、セクションを埋めることにはない。

## 任意セクション

本当に価値があるときだけ付ける。ほとんどの ADR には不要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：決定が再検討されうる場合に有用
- **検討した選択肢**：却下した代替案を覚えておく価値がある場合のみ
- **帰結**：自明でない下流への影響を明記すべき場合のみ

## 採番

`docs/adr/` 内の最大番号をスキャンして +1 する。

## ADR を提案する条件

以下の3つを**すべて**満たすこと：

1. **戻しにくい**：あとで方針転換するコストが大きい
2. **文脈なしでは不可解**：未来の読者がコードを見て「なぜこんなことを？」と不思議に思う
3. **実際のトレードオフの結果**：本物の代替案があり、特定の理由でこれを選んだ

戻しやすい決定なら記録不要（戻せばいいだけ）。驚きがなければ誰も理由を疑問に思わない。代替案がなかったなら「当たり前のことをした」以上に記録することがない。

### ADR に値するもの

- **アーキテクチャの形**：「モノレポにする」「書き込みモデルはイベントソーシング、読み取りモデルは Postgres に射影」
- **コンテキスト間の統合パターン**：「Ordering と Billing はドメインイベントで通信し、同期 HTTP は使わない」
- **ロックインを伴う技術選定**：DB、メッセージバス、認証プロバイダ、デプロイ先。すべてのライブラリではなく、差し替えに四半期かかるものだけ
- **境界とスコープの決定**：「顧客データは Customer コンテキストが所有し、他コンテキストは ID 参照のみ」。明示的な「やらないこと」は「やること」と同じくらい価値がある
- **自明な道からの意図的な逸脱**：「X という理由で ORM ではなく生 SQL を使う」。普通の読者が逆を想定するもの。次のエンジニアが意図的な設計を「修正」してしまうのを防ぐ
- **コードから見えない制約**：「コンプライアンス要件で AWS が使えない」「パートナー API 契約によりレスポンスは 200ms 以内」
- **却下理由が自明でない代替案**：微妙な理由で GraphQL を見送って REST にしたなら記録する。さもないと半年後に誰かがまた GraphQL を提案する
