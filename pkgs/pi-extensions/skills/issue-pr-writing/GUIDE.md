# AIPR 文章ガイド（Linear + GitHub PR）

## このスキルの対象

Linear の Issue タイトルと description、Project summary と description、コメント・ステータス更新に加えて、GitHub PR 本文の作成、編集、レビューを対象にする。

このガイドは自己完結しており、実行時に他のスキルを読まない。参照するのは同じバンドル内の `templates.md`、`aipr-glossary.md`、`examples.md` だけである。

リリースノート、Linear API / MCP による書き込み手順、GitHub 上での PR 作成・更新操作、コードの実装方針、**PR タイトルの生成**は対象外とする。文章を作成しても、エージェントの判断だけで Linear や GitHub を更新しない。

## 使う順序

1. 依頼が Issue、Project、コメント・ステータス更新、PR 本文のどれかを判定する。
2. [テンプレート](templates.md)の該当スキーマで骨組みを作る。
3. このガイドの文章規範に従って本文を書く（PR 本文は「PR 本文の規範」も併読する）。
4. 自己点検チェックリストで不足や曖昧さを確認する。
5. 人が内容を確認した後、権限を持つ人が Linear へ反映する、または明示依頼があれば GitHub の既存連携（`gh` 等）が PR を更新する。スキル自体は文章のみを返す。

## 文章規範

<!-- norms:body -->

### 一段落一トピック

一つの段落では一つの話題だけを扱い、最初の文で主題が分かるようにする。読み手が段落を拾い読みしても論点を追えるためである。

### 事実・推論・未確認を分ける

確認済みの事実、事実から導いた推論、まだ確認していない内容を混ぜない。Linear では文頭または箇条書きに「事実」「推論」「未確認」のラベルを付ける。

### 因果の機構を書く

因果を主張するときは、原因が結果を生む機構を一文で書く。「A だと B」だけでは調査や反証ができないためである。

### 冗長な言い換えを削る

同じ主張を別の表現で繰り返さず、一度だけ具体的に書く。重複を減らすと、更新時の矛盾を防げる。

### LLM 定型句を使わない

内容を増やさない定型句は削る。「重要なのは」「〜において」「多角的」「包括的」「掘り下げる」「正面から」「〜に他ならない」「まとめると」を言い換えだけの目的で使わず、「さらに」「また」「加えて」を連打しない。

### 空欄テンプレートを残さない

完成文に空の `- `、空の `- [ ]`、スキーマの説明文やプレースホルダーを残さない。空欄は作業途中と完成済みを区別できなくする。

### 完了条件を検証可能にする

完了条件には、誰が何をできる、何が表示される、何が返るなどの観測できる状態と、Stg で確認する、テストが通る、件数が 0 になるなどの確認手段を書く。「実装する」のような実装手段の羅列だけでは完了としない。

### 不足情報を創作しない

根拠が足りない数値、担当、期日、承認手順は断定しない。`?` を付けるか「確認事項」とし、誰に何を確認するかを書く。

### 固有名で責務と環境を示す

「システム」「基盤」「環境」で済ませず、[AIPR 用語集](aipr-glossary.md)に従って Web、Core、Patent DB、Stg、Prd などを明記する。責務や出荷段階の取り違えを防ぐためである。

### 固定スキーマを守る

見出しは固定スキーマから増やさず、順序を変えない。差分レビューと検索で同種の文書を比較できる状態を保つ。

### タイトルを結果まで書く

Issue タイトルは「対象 + 変更 + 結果」を 1 句、40 字目安で書き、「対応」「改善」だけで終わらせない。`AIPR-###` は Linear が付与するためタイトルに含めない。

## PR 本文の規範

Linear の文章規範（一段落一トピック、事実・推論・未確認を分ける、冗長な言い換えを削る、LLM 定型句を使わない、空欄テンプレートを残さない、固有名で責務と環境を示す、固定スキーマを守る）は PR 本文にもそのまま適用する。加えて、PR 本文には次を適用する。

### 主張を接地する

`## 変更内容`・`## 検証`・`## 影響範囲・リスク` の記述は、git diff の内容、実際に実行して得られた検証出力、関連 Linear Issue、または依頼者から与えられた context のいずれかに根拠を持たせる。これらのいずれにも根拠がない主張は書かない。

### 実行していないことを実行済みと書かない

未実行のテスト、未確認の影響環境、未確定のレビュアー、評価していないリスク、確認していない Issue ID、確認していないデプロイ状態を断定しない。根拠がなければ `?` または「未確認」と明示し、何を確認すれば埋まるかを書く。

### PR タイトルは対象外

このスキルは PR 本文のテキストのみを扱う。PR タイトルの生成・書き換えは対象外とする。

### テキストのみを返し、書き込みは行わない

スキルは PR 本文の markdown テキストだけを返す。PR の作成・更新は既存の GitHub 連携（`gh` コマンド等）の担当であり、GitHub 連携が無くてもスキルの文章生成自体は機能する。依頼に明示されていない限り、GitHub や Linear へ書き込まない。

### 既定 PR テンプレートが挿入されている場合

`.github/pull_request_template.md` の既定テンプレート（`## 概要` / `## 変更内容` / `## 変更の種類` / `## テスト` / `## 関連Issue` / `## 備考`）が入力に含まれている場合は、本スキルの固定スキーマ（[templates.md](templates.md) の `## PR 本文`）へ置き換える。既定テンプレートの `## テスト` チェック項目に記載された内容は、事実として `## 検証` へ書き写す。既定テンプレートファイル自体は変更しない。

### 短い見慣れた見出しに置き換えない

`## 概要` `## 変更内容` `## テスト`（または `## 動作確認`）`## 備考` のような、GitHub の既定テンプレートや世間一般の PR の書き方に由来する短い 3〜4 見出しだけで済ませない。差分が小さい PR、依頼文が「PR の本文を作成してください」のように固定スキーマへ触れていない自然な言い回しであっても、[templates.md](templates.md) の 8 見出しを省略・改名・並べ替えせずにすべて使う。書くことが少ない節（変更が単一ファイルで `## 変更しないこと` が思いつかない、レビュアーやリスクが軽微など）は、見出しごと削るのではなく「対象外の変更はない」「大きなリスクは無いが、念のため〜を確認してほしい」のように一文で埋める。

## 自己点検チェックリスト

- [ ] A1: 文書種別に合う固定見出しが、追加や順序変更なく並んでいる。
- [ ] A2・A3: 空の箇条書き、空のチェックボックス、説明文、プレースホルダーが残っていない。
- [ ] A4: LLM 定型句と、内容を増やさない接続語の連打がない。
- [ ] A5: 完了条件が観測できる状態と確認手段を含み、実装手段だけで終わっていない。
- [ ] A6: 未確定情報を `?` または確認事項として示し、創作していない。
- [ ] A7・A8: 環境と責務を Stg / Prd、Web / Core / Patent DB などの固有名で示している。
- [ ] A9: コメントでは事実・推論・未確認を区別している。
- [ ] A10: Linear や GitHub への書き込み・更新済みの断定を行わず、文章本文だけを出している。
- [ ] A11: PR 本文の主張が git diff・実際の検証出力・関連 Issue または与えられた context のいずれかに接地している。
- [ ] A12: PR 本文の各節に空節（見出しのみで本文が無い、または「なし」の理由説明を欠く空欄）が残っていない。
- [ ] A13: `## レビューしてほしい点` が対象ファイル・関数・観点など具体的な箇所を指しており、「全体的にレビューしてください」のような抽象的表現だけで終わっていない。
- [ ] A14: `## 影響範囲・リスク` が Web / Core / Patent DB のどの責務・どの環境（Stg / Prd）に影響しうるかを具体的に書いている。
