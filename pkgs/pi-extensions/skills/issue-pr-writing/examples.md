# AIPR 文章の例（Linear + GitHub PR）

すべて匿名化した例であり、実在の Issue、顧客、個人を示さない。

## 例 1: 見出しとテンプレート文を整える

### 悪い例

```markdown
## 内容

何をするのか、なぜやるのかを 1〜3 行で。

### TODO

- Web を直す
-
```

### 良い例

```markdown
タイトル: 特許分析一覧の再読込で最新ステータスを表示する

## 概要

Web の特許分析一覧を再読込したとき、最新の分析ステータスを表示する。

## 背景・現状

事実: Stg では再読込後も更新前のステータスが表示される。

## やること

- Web の一覧取得後に最新ステータスを描画する。

## やらないこと（スコープ外）

- Core の分析処理は変更しない。

## 完了条件

- [ ] Stg で一覧を再読込すると、Web に最新ステータスが表示される。

## 参考情報

- Issue 参照: AIPR-XXX
```

固定見出しへ揃え、説明文と空欄を実際の情報へ置き換えた。

## 例 2: 完了条件を結果で書く

### 悪い例

```markdown
## 完了条件

- [ ] API を実装する
- [ ] テストを追加する
```

### 良い例

```markdown
## 完了条件

- [ ] Web の内部 API が有効な Expr に対して Patent DB の検索件数を返す。
- [ ] 無効な Expr のテストが通り、Web の内部 API が 400 を返す。
```

作業項目ではなく、観測できる応答と確認手段で完了を判定できるようにした。

## 例 3: 責務と環境を明記する

### 悪い例

```markdown
システムが環境で落ちたので対応しました。もう大丈夫です。
```

### 良い例

```markdown
現状: Stg 反映済み。Web の特許分析結果画面を再表示できる。

根拠:
- 事実: Stg で Web の結果 API が 200 を返し、画面が表示された。
- 推論: なし。復旧原因はまだ切り分けていない。
- 未確認: Core の同時実行時にも再発しないかは未確認。

次の一手: 開発担当が Core の同時実行テストを確認する。

確認事項: Prd 反映の出荷承認者と手順を運用責任者に確認する。
```

Web と Core の責務、Stg の出荷段階、確認済みと未確認の範囲を分けた。

## 例 4: 未確定の数値を残す

### 悪い例

```markdown
テナント A では毎日 30 件の検索に失敗しているため、すぐ修正する。
```

### 良い例

```markdown
## 背景・現状

事実: テナント A から、Stg の Patent DB 検索が失敗するとの報告がある。

未確認: 失敗件数は 1 日あたり ? 件で、Web と Patent DB のログ照合が済んでいない。

確認事項: 開発担当が Web と Patent DB の Stg ログを照合し、対象期間と失敗件数を確認する。
```

根拠のない数値を断定せず、確認する対象と手段を示した。

## 例 5: 検証の接地とスコープ境界

### 悪い例

```markdown
## 概要

バグを直しました。

## 変更内容

いろいろ修正しました。

## 検証

テストはたぶん通っています。

## レビューしてほしい点

全体的にレビューしてください。
```

見出しが固定スキーマと一致せず、変更内容も検証も git diff や実行結果に接地していない。レビュー観点が具体箇所を指していない。

### 良い例

```markdown
## 概要

Web の特許分析結果画面で、テナント A の Expr が空文字のとき検索件数が 0 と誤表示される不具合を修正する。

## 背景

事実: Stg でテナント A が空の Expr で検索すると、Patent DB は 400 を返すが、Web は件数 0 として画面表示していた。

## 変更内容

- `aipatentrocket/modules/patent_analysis/services.py` の `search()` を変更し、Patent DB が 400 を返した場合は件数ではなくエラーメッセージを画面へ返すようにした。

## 変更しないこと

- Patent DB 側の Expr 検証ロジックは変更しない。

## 検証

- `docker compose exec --env DJANGO_ENV=test django uv run ./manage.py test aipatentrocket.modules.patent_analysis` を実行し、追加した空 Expr のテストを含め全件成功した。
- Stg での確認は未実施のため `?`。

## 影響範囲・リスク

- Web の特許分析結果画面のみに影響する。Core と Patent DB への変更はない。Prd への影響は Stg 確認後に判断するため現時点では未確認。

## レビューしてほしい点

- `services.py` の `search()` で 400 とその他のエラーコードを区別する条件分岐が、既存の他エラーハンドリングと重複していないか。

## 関連情報

- 関連 Issue: AIPR-XXX
```

固定スキーマの 8 見出しをこの順序で満たし、変更内容と検証を git diff・実行結果に接地させ、レビュー観点を具体箇所まで絞った。

## 例 6: cross-repo と Stg/Prd 出荷段階の書き分け

### 悪い例

```markdown
## 概要

Core の分析ロジックを直してデプロイ済みです。

## 検証

問題ありません。

## 影響範囲・リスク

特にありません。
```

「デプロイ済み」が Stg か Prd かを区別せず、出荷承認の有無にも触れていない。見出しも固定スキーマの 8 見出しを満たしていない。

### 良い例

```markdown
## 概要

Core（`containers/patent_analysis_core/ai_patent_rocket_mvp` submodule）のクラスタリング処理で、入力 0 件のとき例外が発生する不具合を修正し、Web 側の呼び出し確認結果を反映する。

## 背景

事実: Core のバッチが入力 0 件のとき未捕捉例外で異常終了していた。Web 側は当該ジョブの status を `failed` のまま表示していた。

## 変更内容

- Core: `patent_analysis/clustering.py` で入力 0 件を早期リターンする分岐を追加した。
- Web: `aipatentrocket/modules/patent_analysis/services.py` の submodule 参照を更新した。

## 変更しないこと

- Web の画面表示ロジックは変更しない。

## 検証

- main マージ後、`Deploy to STG` が成功し、Stg の Web で入力 0 件のジョブを再実行して `completed` になることを確認した。
- Prd への `Deploy to PRD`（`release-*` ブランチ経由）は未実行。

## 影響範囲・リスク

- Core のクラスタリング処理と、Web の submodule 参照更新に影響する。Patent DB への影響はない。現在の出荷段階は Stg 反映済みであり、Prd 反映済みではない。Prd 反映前の出荷承認者と承認手順は未確認。

## レビューしてほしい点

- `clustering.py` の早期リターンが、入力 1 件以上の既存経路の挙動を変えていないか。

## 関連情報

- 関連 Issue: AIPR-XXX
- Core 側の対応コミットは submodule 参照更新に含まれる。
```

Stg 反映済みと Prd 反映済みを明確に区別し、出荷承認者が未確認であることを断定せずに書いた。Web と Core の責務を分けて変更内容を記述した。
