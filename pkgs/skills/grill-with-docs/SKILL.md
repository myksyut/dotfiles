# grill-with-docs — ドキュメント駆動グリル

計画・決定・アイデアについて、共有理解に到達するまで容赦なくインタビューする。
さらに、確定した用語と意思決定を **その場で** `CONTEXT.md` と ADR に書き残す。

## 起動時にやること

1. リポジトリの `CONTEXT-MAP.md` → `CONTEXT.md` → `docs/adr/` の順に存在を確認し、既存の用語と意思決定を読み込む
2. 進行中のワークフロー成果物があれば読み、グリル対象の前提とする。存在するものだけでよい：
   - `context-os/specs/<date>-<feature>/`（SPECモード: initialization.md / requirements.md / spec.md）
   - `.context/todo.md`（PLANモードのプラン）
   - その他 `/reports` の既存プラン・リサーチ記録など、話題に関連するもの
3. どれも無ければそのまま開始してよい（ファイルは**遅延作成**：書くことができて初めて作る）
4. マルチコンテキストの場合（`CONTEXT-MAP.md` あり）は、今の話題がどのコンテキストに属するか推測し、不明なら質問する

### ワークフロー成果物との役割分担（原則）

**このスキルが書くのは常設ドキュメント（`CONTEXT.md` / `docs/adr/`）だけ。**
ワークフロー成果物（プラン・スペック・レポートなど）はそれを生成したワークフローの管轄であり、
このスキルは読むだけで勝手に書き換えない（記入はホストのモードフローに従う）。

| 成果物の例 | 管轄（書き先） | 寿命 |
| ------------ | ---------------- | ------ |
| プラン・TODO | `.context/todo.md`（PLANモード） | タスク単位 |
| 要件・スペック | `context-os/specs/`（SPECモード） | 機能単位 |
| リサーチ記録・完了レポート | `/reports` ・ research セッション | 調査/作業単位 |
| **確定した用語** | **`CONTEXT.md`（このスキル）** | **リポジトリ常設** |
| **確定した意思決定** | **`docs/adr/`（このスキル）** | **リポジトリ常設** |

振り分けルール（どのワークフロー中でも同じ）：

- グリルで確定した**用語** → `CONTEXT.md` へ即更新
- **ADR 3条件を満たす意思決定** → `docs/adr/` へ
- それ以外（要件・タスク・設計メモ） → 進行中のワークフロー成果物へ（そのモードのフローで）
- ワークフロー成果物からは関連 ADR を**リンク参照**し、内容を重複させない
- 逆方向も同様：一時成果物に埋もれた用語・決定に常設の価値が出たら、このスキルが `CONTEXT.md` / ADR へ**昇格**を提案する

## グリルの進め方（デザインツリー方式）

意思決定を**デザインツリー**として捉える：各決定はその下にぶら下がる決定へと枝分かれする。

**ラウンド制**で進める。**フロンティア**とは、前提がすでに確定していて「いま推測なしで聞ける質問」の集合。
フロンティア全体を1ラウンドで一括提示し、各質問に番号と推奨回答を付け、ユーザーの回答を待つ。

ラウンドのフォーマット：

```text
❓ **Q1** - **<質問タイトル>**: <質問本文。複数段落・選択肢提示も可>

➡️ <推奨回答>

---

❓ **Q2** - **<質問タイトル>**: <質問本文>

➡️ <推奨回答>
```

- 回答を得るたびにツリーが再構成される：確定した決定がフロンティアを外側へ押し広げ、依存していた質問が解禁される。フロンティアを再計算して次のラウンドへ
- 同一ラウンド内の別の質問の答えに依存する質問は、**後のラウンド**に回す
- **事実調査は AI の仕事、ユーザーの仕事ではない**。ファイルシステムやコードで解決できる疑問はサブエージェントを派遣するか自分で調べる。調査中も待たずに、その下流以外のフロンティアは先に聞く
- **意思決定だけ**をユーザーに委ね、回答を待つ

## セッション中のドキュメント規律

### 用語集と照合して指摘する

ユーザーの用語が `CONTEXT.md` の定義と矛盾したら即座に指摘する。
「用語集では『キャンセル』はXと定義されていますが、今の話はYに聞こえます。どちらですか？」

### 曖昧な言葉を研ぐ

曖昧・多義的な用語には正準語を提案する。
「『アカウント』と言っていますが、Customer と User のどちらですか？ 別物です」

### 具体的なシナリオで検証する

ドメインの関係性が話題になったら、エッジケースを突くシナリオを発明して境界を精密にさせる。

### コードと突き合わせる

ユーザーの説明とコードの実態が食い違っていたら表面化させる。
「コードは Order 全体をキャンセルしていますが、今『部分キャンセル可能』と言いましたね。どちらが正ですか？」

### CONTEXT.md はその場で更新する

用語が確定したら**即座に** `CONTEXT.md` を更新する。バッチしない。
フォーマットは [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) に従う。

`CONTEXT.md` は用語集であり、それ以外の何物でもない。仕様書・メモ帳・実装決定の置き場にしないこと。

### ADR は控えめに提案する

以下の3条件を**すべて**満たすときだけ ADR 作成を提案する：

1. **戻しにくい**: あとで方針転換するコストが大きい
2. **文脈なしでは不可解**: 未来の読者が「なぜこうした？」と不思議に思う
3. **実際のトレードオフの結果**: 本物の代替案があり、特定の理由でこれを選んだ

1つでも欠けたら ADR は書かない。フォーマットは [ADR-FORMAT.md](./ADR-FORMAT.md) に従う。

## PLANモードの必須チェックポイント

agent-piのPLANモードでは、Plannotatorを開く前に必ずgrillを完了する。

1. `CONTEXT-MAP.md` → `CONTEXT.md` → `docs/adr/` と関連するworkflow成果物を読み込む
2. チャットまたは `ask_user_question` で前提・用語・意思決定をラウンド制で詰める
3. grillの結論を含む計画を `.context/todo.md` に書き、`## Grill checkpoint`（要約・決定・未解決質問0件）を含める
4. `grill_with_docs { plan_file_path: ".context/todo.md", summary: "...", decisions: [...], open_questions: [] }` を呼び、現在の計画バイト列へcheckpointをbindする
5. その同じ `.context/todo.md` だけを `plannotator_review` に渡す。Plannotatorで表現や実装詳細だけが修正された場合は同じcheckpointで再レビューし、用語・前提・方針が変わった場合だけgrillを再実行する

`grill_with_docs` が利用できない、要約が空、または未解決質問が残っている場合は、計画承認や実装へ進まない。Plannotator自体が利用できない場合は、grill完了後に限りチャット承認へfallbackできる。

### Claude Code での同等手順

`grill_with_docs` ツールは Pi 専用。Claude Code では次で bind する。

1. 手順 1–3 は同じ（`.context/todo.md` に `## Grill checkpoint` と Open questions: none）
2. 承認後に `.context/.grill-gate.json` へ `{ "approved": true, "planHash": "<sha256 of todo.md>" }` を書く
3. レビューは Plannotator plugin（`/plannotator-review` または Plan mode の intercept）。無ければチャット承認
4. PreToolUse hook が未承認の `Write`/`Edit` を拒否する

## レビューUI（重要）

- agent-pi の削除済み View 系ツール（`show_plan` / `show_spec` / `show_file` / `show_report`）は**使わない**
- 成果物（プラン・スペック・ADR ドラフト）をレビューに出すときは、利用可能なら **`plannotator_review`**（Pi）または Plannotator plugin（Claude Code）を使う
  - Pi: `plannotator_review { file_path: "<document.md>", title: "<title>" }`
  - Claude Code: `.context/todo.md` を Plannotator に渡し、承認後 `.context/.grill-gate.json` を書く
  - どちらも使えない場合は、本文と判断項目をチャットへ提示し、ユーザーの返信を待つ
- ラウンド制の質問自体はチャット内の ❓/➡️ フォーマット（または `ask_user_question` / `AskUserQuestion`）で行う

## 終了条件

フロンティアが空になったら終わり：デザインツリーの全分岐を訪問済みで、暗黙の前提が残っていない状態。
ユーザーが「共有理解に達した」と確認するまで、**実装には着手しない**。

## 言語

質問・指摘・`CONTEXT.md`・ADR はすべて**日本語**で書く（コード内の識別子・正準語そのものは英語でよい）。
